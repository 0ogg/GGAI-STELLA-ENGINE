# 스텔라 폰 v2 설계서 — 전면 마이그레이션 & 업그레이드

> **문서 지위**: 폰 v2 개편의 설계 진실 소스. 기존 `스텔라폰 스펙.md` 는 v1(현재 동작) 기록으로 유지하고,
> v2 단계가 구현·검증될 때마다 해당 내용을 스펙에 흡수하고 이 문서의 그 절을 정리한다.
> v1 의 핵심 원칙(폰 ID=페르소나, 아는 것만 안다, 세션 본문 불변, 비용 상한, byte 동일 대전제)은 v2 에서도 전부 유효.

## 0. 개편 목표

1. **토큰 설계 상향** — 수많은 세션·프로필이 들어가는 작업에 맞는 예산 체계 (자 단위 → 토큰 단위 통일).
2. **SNS 를 "진짜 간이 SNS" 수준으로** — 영속 계정 DB, 이슈 등급, 알고리즘 반응 분배. 생성 1회로 새 게시글+댓글+사진이 함께 갱신.
3. **문자를 기계적 핑퐁이 아니라 리얼하게** — 시간차 배달, 읽음, 이어 보내기.
4. **이미지 이해 파이프라인** — 출처별로 올바른 텍스트 정보를 뽑아 "그림이 아니라 사진"으로 취급.
5. **스텔라튜브(스트리밍) 독립 앱화** — 세션 노드와 연동된 실시간 방송 + 채팅 + 도네이션.
6. **앱 간 정보 공유 허브** — 문자/SNS/튜브가 최근 이슈를 공유, "봤는지" 판정.
7. **외부 확장 진입점** — 서드파티가 폰에 앱을 추가할 수 있는 등록 API.
8. **디자인 전면 재작업** — "진짜 폰 같다"는 레퍼런스에 걸맞은 CSS 시스템.

## 1. 공통 기반

### 1.1 토큰 예산 재설계 (전부 설정 가능, 아래는 기본값)

| 항목 | v1 | v2 기본값 | 비고 |
|---|---|---|---|
| 문자: 세션 장면 첨부 | 1200자 | **2000 토큰** | 자 → 토큰 단위 통일 |
| 문자: 이력 첨부 | 40통 | 60통 | |
| SNS: 확정 시나리오 개수 | 세션 3개 | **3개** (`snsConfirmedCount`) | 세션 아닌 "시나리오(인물)" 단위로 변경 |
| SNS: 시나리오당 요약 첨부 | 800자 | **2000 토큰** (`snsSummaryTokens`) | 최근분 우선(tail) |
| SNS: 시나리오당 본문 첨부 | 800자 | **2000 토큰** (`snsBodyTokens`) | 최근분 우선(tail) |
| SNS: 활성 로어북 | 있음 | **본문 첨부량 기준 매칭 전부** (`snsIncludeLore` 기본 켬) | 상시+키워드 매칭, 절단 없음 |
| SNS: 로스터(비확정 참고) | 10세계 × 1400tok | 10인 × 1400tok | 설명+로어북 head 압축 |
| SNS: 랜덤 세션 | 없음 | 체크 시 **2개 고정**, 각 항목 토큰 = 확정값의 50% (`snsRandomSessions`) | |
| SNS: 피드 발췌 | 8개 | 20개 (등급 가중) | §6.4 |
| 앱 간 공유 다이제스트 | 없음 | **1000 토큰** (`sharedContextTokens`) | 자기 앱 제외 |

- 모든 절단은 기존 `trimToTokens`(tail=최신 우선) 재사용. 토큰 카운트는 `ai.countTokens`.
- 예상 비용: SNS 갱신 1회 입력 ≈ 3×4000 + 2×2000 + 로스터 ~10000 + 피드/공유 ~3000 ≈ **25k~30k 토큰**. 설정에서 낮출 수 있으므로 기본값은 품질 우선.

### 1.2 데이터 파일 맵 (v2)

```
GGAI/PHONE/
├── <personaId>/messages.json    # v2: 메시지에 deliverAt/readAt 추가 (§3.2)
├── sns.json                     # v2: 게시글에 issueScale/accountId 추가 (§6)
├── accounts.json                # 신규: SNS 영속 계정 DB (§6.1)
├── shared-digest.json           # 신규: 앱 간 공유 이슈 캐시 (§8, 재계산 가능한 파생 캐시)
└── assets/

GGAI/SCENARIOS/<이름>/SESSIONS/<세션>/
└── stream.json                  # 신규: 스텔라튜브 방송 + 노드별 반응 (§7.1)
```

- 전부 StellaStore 경유(신규 메서드 + `phone-*-changed` 이벤트). 저장(JSON)과 표시 계층 분리 원칙 유지.
- **마이그레이션은 normalize 에서 무손실로**: v1 파일은 필드가 없을 뿐이므로 읽기 시 기본값 보충(기존 `normalizePhoneMessages` 패턴). 파일 덮어쓰기는 다음 저장 때 자연 발생. 별도 일괄 변환 없음.
  - `accounts.json` 초기 구축: 첫 로드 때 기존 sns.json 의 작성자(핸들 우선 키)를 스캔해 계정으로 등록(백필).
  - 구 `stream` 게시글(`SnsPost.stream`)은 레거시 표시만 유지, 새 방송은 전부 stream.json 경로.

## 2. 디자인 시스템 — "진짜 폰"

전면 CSS 재작업. 지금처럼 화면별로 땜질하지 않고 **폰 전용 디자인 토큰 + 앱별 스킨** 2층으로 재구축한다.

### 2.1 폰 디자인 토큰 (`.ggai-phone-root` CSS 변수)

- `--phone-bg`(OLED 검정 프레임), `--phone-screen-bg`, `--phone-accent`, `--phone-radius`(연속 코너), `--phone-font`(시스템 산세리프 고정 — 옵시디언 테마 서체에 오염되지 않게), `--phone-hairline`(1px 분리선), 라이트/다크 두 벌.
- 상태 바: 시계(실시간) + 신호/와이파이/배터리 아이콘(장식) + 로그인 페르소나 칩. 모든 앱 공통.
- 하단 내비: 홈 알약(제스처 바 스타일). 기존 ‹/● 가상 버튼 계승하되 시각만 재작업.
- 테마 격리 리셋(`:where(button/textarea)` + `.ggai-phone-screen` 접두 승리 규칙)은 v1 그대로 유지 — 새 클래스도 이 규칙 준수.

### 2.2 앱별 스킨 레퍼런스

| 앱 | 레퍼런스 | 핵심 |
|---|---|---|
| 메시지 | iOS 메시지/카톡 | 말풍선 스킨은 챗 세션 공용 클래스 유지(회귀 방지), 폰 안에서 여백·크기만 재조정. 타이핑 인디케이터(···), 읽음 표시 |
| 스텔라 네트워크 | 인스타+트위터 하이브리드 | 카드형 피드, 하트 애니메이션, 등급 3+ 이슈 배지, 팔로워 수 표시 |
| 카메라 | 실제 카메라 앱 | 뷰파인더(결과 미리보기 영역) + 하단 셔터 원버튼 + 좌우 보조 버튼(갤러리/모드). 지금의 "정렬 안 된 웹폼" 전면 교체 |
| 스텔라튜브 | 유튜브 라이브/트위치 | 상단 방송 화면(장면 텍스트/삽화 썸네일) + 우측/하단 실시간 채팅 컬럼 + 시청자 수·도네이션 오버레이 |

- 구현 순서상 CSS 는 마지막 단계(V2-8)에 몰아서 하되, 새 화면(튜브·카메라)은 만들 때부터 토큰 기반으로 작성.

## 3. 문자 v2

UI 골격(스레드 목록 ↔ 대화창)은 유지. 아래만 바꾼다.

### 3.1 연락처 관리 — 체크 목록

- [연락처 등록] 버튼 → 현재의 순차 메뉴 대신 **전용 모달**: 후보 시나리오 전체를 "표지 썸네일 + 이름" 그리드/리스트로, 등록된 항목은 체크 표시.
- **체크 = 등록, 체크 해제 = 연락처 삭제**(스레드 삭제 동반은 v1 과 동일하게 확인 모달 1회). 저장은 기존 `registerContact`/`unregisterContact` 재사용.
- 후보 파생 로직(`listPhoneContacts`)은 유지 — 그 페르소나로 세션을 함께 한 시나리오만.

### 3.2 리얼 문자 메커니즘 — 배달 파이프라인

핵심: 생성 결과를 **한 번에 다 꽂지 않고**, 답장 계획(JSON)을 받아 시간차로 배달한다.

**답장 생성 출력 (JSON 프로토콜, `phone-prompts.ts` 에 IO 명세 추가)**
```json
{
  "read": true,              // 읽었는가 (false = 읽씹/나중에 읽음)
  "messages": [
    { "text": "...", "delaySec": 4 },   // 앞 메시지로부터의 간격 (타이핑 시간 느낌)
    { "text": "...", "delaySec": 12 }
  ],
  "replyDelaySec": 30        // 읽고 나서 첫 답장까지 (0 = 즉답, 최대 캡 상한)
}
```

**배달 알고리즘**
1. 생성 직후 메시지들을 `deliverAt = now + replyDelay + Σdelay` 로 저장(`PhoneMessage.deliverAt`). `deliverAt` 이 미래인 메시지는 목록/스레드에 **표시하지 않는다**.
2. 폰 스케줄러 1분 틱 + 폰 뷰가 열려 있으면 5초 틱으로 `deliverAt ≤ now` 를 "배달"(표시 + 수신 Notice). 뷰에서는 배달 직전 타이핑 인디케이터(···) 말풍선 표시.
3. `replyDelaySec` 상한 = 설정 `maxReplyDelayMinutes`(기본 10분, 0=즉시 배달 모드 → v1 동작). 옵시디언이 꺼져 있던 시간은 캐치업하되 **한 번에 몰아 배달**(밀린 것을 순차 연출하지 않음 — 버스트 방지 원칙).
4. `read:false` 응답 = 저장만 하고 답장 없음("1" 유지). 다음 갱신 틱에서 그 스레드는 "밀린 답장 후보"로 우선 처리(미응답 상한 계산에서 캐릭터 쪽 미답도 카운트).
5. **이어 보내기(double-texting)**: 캐릭터 선발신 로직이 "내가 마지막으로 보냈지만 답이 없는" 스레드에도 낮은 확률(가중치 절반)로 한 번 더 보낼 수 있게 허용(현행 금지 규칙 완화, 스레드당 연속 2회 상한).
6. 프롬프트 기조(편집 가능한 `phoneText` 기본값에 반영): 짧은 반응(ㅋㅋ/이모지/스티커성 한 마디)·사진만 답장 허용, 문어체 금지, 상황(세션 중/새벽)에 맞는 템포.

- 읽음 표시: `readAt` 저장, 페르소나 발신 말풍선 옆에 "읽음" 소표시(상대가 답장 생성을 시작한 시점 = 읽음).
- **결정 필요**: 시간차 배달을 기본 켬으로 할지(추천: 켬, `maxReplyDelayMinutes=10`), 즉답 선호 사용자는 0 으로.

### 3.3 사진 첨부

- 컴포저 사진 버튼(v1 유지). 첨부 정보 텍스트는 §5 이미지 파이프라인의 산출물(캡션)을 사용 — 문자 이력/세션 주입 동봉 형식 `[photo: 캡션]` 유지.

## 5. 이미지 이해 파이프라인 (공용 신규 모듈)

문자/SNS/튜브 어디서든 이미지를 첨부하면, **모델에게 줄 텍스트 정보(description)와 취급 지시(announce)** 를 뽑는 단일 함수로 통일한다.

```
resolveImageInfo(asset) → { description, source, announce }
```

### 5.1 출처 판별 순서와 정보 소스

| 출처 | 판별 | description | announce |
|---|---|---|---|
| A. 카메라 촬영 / 사용자 캡션 | 폰 갤러리 `source:"camera"|"upload"` | 사용자가 입력한 장면 묘사 or 직접 프롬프트 or 업로드 캡션 | "카메라로 찍은 실제 사진" |
| B. 세션 삽화 | 세션 illustrations 항목 | **그 삽화의 `IllustrationVariant.prompt` 중 장면 부분만** — 재생성 버튼에 뜨는 LLM 생성 프롬프트. 메인 프롬프트(퀄리티 태그 합성분)는 제외 | "실제 사진으로 취급. 아래는 사진 내용 묘사" |
| C. 기타 AI 생성 이미지 (메타데이터 있음) | PNG tEXt/iTXt 파싱(`png-chunk.ts` 확장): NAI `Comment` JSON, A1111 `parameters`, ComfyUI `prompt` | 파싱한 **메인 프롬프트 + 캐릭터 프롬프트 전체** | "이것은 이미지 생성 프롬프트 원문이다. 퀄리티/스타일 태그는 무시하고, 내용 태그가 묘사하는 장면이 **실제로 찍힌 사진**이라고 간주하라" |
| D. 읽을 수 없는 이미지 (진짜 사진 등) | 메타데이터 없음 | **비전 모델**로 1회 묘사 생성 → 갤러리 캡션에 저장(캐시, 재호출 없음) | "실제 사진" |
await ggai.chat({
  messages: [{
    role: "user",
    content: [
      { type: "text", text: "이 이미지 설명해줘" }, //결과를 좀 더 디테일하게 받을 수 있도록 프롬프트 손볼 것
      { type: "image", source: { kind: "base64", mediaType: "image/png", data: "<base64>" } },
      // 또는: { type: "image", source: { kind: "url", url: "https://..." } }
    ],
  }],
});
- B 의 "장면 부분만": 현 구조에서 이미 충족 — 메인(퀄리티) 프롬프트는 Core 이미지 프로필 소관이라 `IllustrationVariant.prompt` 에는 장면 프롬프트만 저장된다(삽화 피커 캡션도 이 값). 별도 `scenePrompt` 분리 불필요 (V2-3 구현 시 확인).
- C/D 는 첨부(업로드) 시점에 1회 실행하고 결과를 갤러리 항목 캡션에 저장 — 생성 때마다 반복하지 않는다.

### 5.2 설정 (폰 패널 "이미지" 묶음)

| 설정 | 기본값 |
|---|---|
| 그림(이미지) 모델 | 기존 `imageProfileId` 유지 |
| AI 의 사진 게시 허용 (SNS photo 생성) | 켬 |
| 비전 모델 선택 (`visionProfileId`, 챗 프로필 중) | 미지정 |
| 비 AI 이미지에 비전 모델 사용 (출처 D) | 켬 (비전 모델 지정 시) |
| AI 그림에도 비전 모델 사용 (출처 B·C 를 비전 묘사로 대체) | 끔 |

### 5.3 선행 과제 — Core 비전 입력

~~선행 과제~~ **해소됨(V2-7)**: Core 의 `chat()` 은 이미 `content` 배열(`{type:"image", source:{kind:"base64"|"url"}}`)을 받는다(vision 지원 모델의 chat 프로필 한정). ## 6. SNS v2 — 스텔라 네트워크

### 6.1 영속 계정 DB — `accounts.json`

"매번 새 이름이 튀어나오는 피드"가 아니라 **같은 사람들이 계속 사는 SNS** 를 만든다.

```json
{
  "version": 1,
  "accounts": [{
    "id": "acc_x1",
    "kind": "character|extra|persona|press",
    "scenarioId": "…",          // character 만
    "name": "…", "handle": "@…", "verified": false,
    "world": "…",
    "followers": 830,            // 좋아요 스케일·시청자 수의 기준
    "persona": "한 줄 성향/말투 메모",  // 생성 시 일관성 재료
    "firstSeen": 0, "lastActive": 0, "postCount": 0
  }]
}
```

- **갱신 규칙**: 배치 파싱 시 핸들 키로 매칭 — 기존 계정이면 그 계정으로 귀속(이름/성향 유지), 새 핸들이면 계정 생성. 생성 프롬프트에는 "기존 계정 목록(활동 많은 순 상위 30)"을 주고 **재등장을 우선**하게 지시(신규 발명은 배치당 상한, 기본 3).
- followers 는 활동/이슈 등급에 따라 완만 증감(엔진이 계산: 게시글 등급별 +, 장기 미활동 −). 유명인/언론(`press`, verified)은 등급 4~5 이슈에서만 출현·생성 허용.
- 페르소나 계정도 여기 등록(팔로워 수 부여) — 사칭 방지 규칙은 v1 유지.

### 6.2 이슈 등급 시스템 (5단계)

게시글마다 `issueScale: 1~5`. **생성 시 모델이 판정**해 JSON 에 부여하고, 엔진이 범위를 강제(클램프)한다.

| 등급 | 의미 | 하트(likes) | 댓글 | NPC 출현 |
|---|---|---|---|---|
| 1 | 노관심 | 1~2 | 0 | 없음 |
| 2 | 일상 | 3~99 | 1~2 | 지인/알고리즘 소수 |
| 3 | 특정 분야 이슈 | 100~999 | 상위 5개 공개 + [더 보기] | 분야 계정 등장 |
| 4 | 국가 이슈 | 1,000~9,999 | 3단계와 동일 | 언론/공식(verified) 등장 |
| 5 | 세계 이슈 | 10,000+ | 3단계와 동일 | 국제 언론/유명인 등장 |

- **평가는 현실적으로, 사용자 계정에 아부 금지** — 프롬프트에 명시. 단 **유저 게시글은 `max(판정, 2)`** 로 클램프(완전 무시 방지) + 세션 컨텍스트상 관계·인맥이 있으면 그 인물의 반응이 우선 배정.
- likes 가 등급 범위를 벗어나면 엔진이 범위로 클램프. 기존 글의 등급은 후속 배치가 상향 조정 가능(이슈가 커지는 서사 — `issueScale` 만 올리고 likes 는 새 범위로 성장).
- UI: 등급 3+ 게시글에 배지(🔥 등), 하트 수는 축약 표기(1.2k, 34k).

### 6.3 반응 분배 알고리즘

배치 프롬프트에 다음 분배 규칙을 고정 IO 로 명시:

- 각 게시글 답글의 **8할 = 그 글을 좋아할 "알고리즘을 탄" 유저의 반응**(관심사 일치·호의).
- **불호 비율 = min(40%, (issueScale − 2) × 15%)** — 이슈가 커질수록 논쟁 유입.
- 유저 게시글 집중 완화: 배치당 유저 글 대상 반응은 이슈 크기에 걸맞게(등급 2면 1~2개). "뷰어 우대" v1 규칙 삭제.

### 6.4 댓글 대상 선정 — 최상단 이슈 1 + 최근 유저글 1 (2026-07-18 사용자 재확정)

- **댓글이 열린 글은 딱 둘**: ①현재 최상단 이슈(붐업 글, `SnsFeedFile.boom = {postId, turns}`) ②뷰어(로그인 페르소나)의 가장 최근 글. **나머지 피드는 추가 갱신 없이 이미 완성된 상태로 동결** — 프롬프트에 컨텍스트 전용으로만 주고, 파서도 열린 두 글 밖 대상 comment 를 폐기(이중 방어). 둘이 같은 글이면 열린 글은 사실상 1개.
- 피드 발췌는 표시 순서(`max(createdAt, bumpedAt)`) 상위 20개 유지 — 새 글 생성의 맥락 재료일 뿐, 댓글 자격과 무관.
- **최상단 이슈 성장 = 반응 기반**: `issueScale +1`(**한도 5**)·likes 재클램프·`bumpedAt` 재부상은 **그 배치에 실제로 댓글을 받았을 때만**. 반응 없는 배치는 성장·재부상 없이 자리만 유지(새 글에 밀려 내려가기 시작), **2배치 연속 무반응이면 이슈가 식어 은퇴**(`boom.quiet`) — 별거 아닌 글이 상단에서 저절로 🔥5 가 되는 일 방지 (2026-07-18 사용자 지적).
- **교체 = 서사적 판정**: 프로토콜의 `"boom": true` 플래그 — 모델이 "현 최상단 이슈보다 **서사적으로** 더 큰 사건"이라고 판단한 새 글(또는 댓글 대상 = 유저 글이 터진 경우)에만 표시. 등급 숫자 비교가 아니라 픽션 속 파장으로 겨룬다. 플래그가 없으면 현 이슈가 계속 탄다.
- **10턴 상한**: 같은 이슈가 10배치 이상 최상단을 유지하지 못한다 — 10턴 도달 시 프롬프트가 교체를 강제(MANDATORY)하고, 모델 지목이 없으면 엔진이 이번 배치 최고 등급 새 글로 강제 교체, 새 글도 없으면 최상단이 빈다(이슈 소멸). 무반응 은퇴(quiet ≥ 2)도 같은 교체 경로.
- 최상단이 빈 상태(첫 배치 포함)에서는 이번 배치 최고 등급 새 글이 자동 선정된다. [더 보기](§6.7)는 사용자 명시 클릭이라 동결과 무관하게 유지.

### 6.5 인풋 컨텍스트 조립 — 참가자 선별

```
1. 후보 풀 = 세션 1개 이상 있는 시나리오 (그룹 세션은 멤버 전원 참가로 계산)
   - 제외 설정(폰 설정 "SNS 참가 시나리오" 체크 해제, `snsExcludedScenarioIds`)은
     **인물(계정) 축에만 작용** — 확정 참가·로스터·작성자 귀속에서만 빠진다.
     그 시나리오의 세션은 장면 재료로 유지되고, **가장 최근 세션은 어떤 경우에도
     무조건 첨부**된다 (프로필 축 ≠ 세션 컨텍스트 축 — 사용자 확정 2026-07-18).
2. 참가율 점수 score(sc) = Σ_{참가 세션 s} 0.5^(경과일(s.modifiedAt)/14)
   (많이·최근에 참가할수록 높음. 그룹 세션은 멤버 전원 가산)
3. 확정 참가 (기본 3, `snsConfirmedCount`):
   - 가장 최근 세션(열린 세션 최우선)의 참가자 → 무조건 확정 (확률 100%)
   - 남은 슬롯 = score 비례 가중 랜덤 비복원 추출
4. 로스터 참고 (총 10인): 확정 제외 나머지에서 score 비례 가중 랜덤 7인
```

**첨부 자료 (시나리오당)**

| 대상 | 자료 |
|---|---|
| 확정 참가 3인 | 카드 설명 + **최근 세션 요약 tail 2000tok** + **본문 tail 2000tok** + 그 본문 기준 활성 로어북 전부(`snsIncludeLore` 기본 켬) |
| 랜덤 세션 2개 (체크 시) | 확정에 안 뽑힌 세션 중 무작위 2개 고정 — 확정과 같은 항목 구성, 각 토큰은 50% |
| 로스터 7인 | 설명 + 로어북 head 압축 1400tok (기존 `buildWorldReference`) |

- 요약 소스 = 세션 summaries(`composeInheritedSummary`), 본문 = `buildSpans` 활성 경로. 열린 세션은 flush 후 fresh 읽기(v1 유지).
- 여기에 §8 공유 다이제스트(SNS 자신 제외분 1000tok) + 피드 발췌 20개 + 계정 목록 30개가 합류.

## 7. 스텔라튜브 — 스트리밍 v2

독립 앱으로 승격(홈 그리드에 아이콘 추가). v1 의 SNS 게시글 내장 방송(`SnsPost.stream`)은 폐기하고 세션 연동 구조로 재설계.

### 7.1 데이터 — 세션 옆 `stream.json`

```json
{
  "version": 1,
  "streamId": "…",
  "streamer": { "accountId": "acc_x1", "name": "…" },  // 페르소나 or 캐릭터 계정
  "live": true,
  "startedNodeId": "…",           // 이 노드 "다음"부터 방송분
  "pendingOff": false,             // §7.3 2연속 off 규칙
  "nodes": {
    "<nodeId>": {
      "viewers": 1520,
      "chat": [ { "account": "@h", "text": "…", "donation": 5000 } ],
      "streamState": "on|closing"  // 모델 판정 원본
    }
  },
  "endedAt": 0
}
```

- **노드 키 저장 = 재생성 연동이 공짜**: 재생성하면 새 sibling 노드 id 로 반응을 새로 생성, 옛 노드의 반응은 그 노드에 남는다(분기 보존 철학 그대로). 표시는 항상 활성 경로(root→activeLeaf) 위 노드들만.
- 방송 종료 시 스텔라튜브 피드(다시보기 목록)에 항목이 남고, SNS 공유 다이제스트에 "방송 있었음" 이슈로 합류.
- 세션 삭제 시 자동 종료(v1 규칙 유지). **방송은 세션당 1개**(파일이 세션 옆 stream.json 하나) — 볼트 전역 동시 1개 제한은 폐지(2026-07-26 사용자 지적: 다른 시나리오 세션으로 옮겨 놀 때 방송을 못 켜는 건 말이 안 된다). 쉬고 있는 방송은 비용이 0이다(반응은 그 세션에 새 노드가 생길 때만 생성). 라이브가 여럿이면 폰 튜브 화면은 지금 열어 둔 세션의 방송을 우선 열고, 아니면 목록을 보여준다.

### 7.2 시작 — 두 경로

1. **수동**: 옵시디언 커맨드 "스텔라튜브 방송 토글" **1개**(켜짐↔꺼짐). 켜면 현재 열린 세션이 방송 대상, 스트리머 = 로그인 페르소나 계정. **페르소나가 스트리머인 방송은 이 경로 전용.**
2. **자동(AI 판정)** — 두 진입점 모두 같은 규칙을 따른다:
   - SNS 갱신 JSON 의 `stream_start` 항목(배치에 얹힌 판정).
   - 세션 생성문의 방송 키워드 — **키워드는 시작 스위치가 아니라 판정 요청 신호다.** 걸리면 장면 tail 을 첨부한 전용 판정 호출 1회(편집 가능한 `phoneStreamDetect` 프롬프트)를 보내 "지금 실제로 방송 중인가 / 누가 켰는가"를 묻는다. 스로틀 3분.
   - **스트리머는 장면 속 인물 명부에서만** 고른다(호스트 시나리오 + 그룹 멤버 + 장면에 이름이 등장하는 기존 계정). 로그인 페르소나는 명부에서 빠진다.
   - 판정이 `live:false` 이거나 지목 인물이 명부에 없으면 **방송을 시작하지 않는다.** 자동 경로의 페르소나 폴백은 없다(오작동보다 침묵이 낫다 — 2026-07-26 사용자 지적).

### 7.3 진행/종료 — 노드 연동 상태기계

```
세션에 새 AI 노드 생성 완료(onGenerationComplete)
  └─ live 방송의 세션이면 → 그 노드 반응 배치 생성:
     입력 = 방송 시작 이후 활성 경로 본문 tail + 직전 노드들의 채팅 흐름
            + 스트리머 계정(팔로워) + 계정 DB 상위 + 공유 다이제스트
     출력(JSON) = { viewers, streamState: "on"|"closing", chat: [{account,text,donation?}] }

streamState 처리:
  on      → pendingOff 해제, 반응 저장
  closing → pendingOff 였으면 → 방송 종료 (live=false)
            아니면 → pendingOff=true, 반응은 정상 저장  ← "클로징 멘트만 했는데 꺼짐" 방지
재생성으로 closing 노드가 대체되면 → 활성 경로 기준으로 pendingOff 재평가
  (방송 끄는 전개를 재생성으로 없애고 이어가는 경우 자동 복구)
```

- off 는 항상 이 2연속 판정 경로. 수동 커맨드 off 만 즉시 종료.
- **가지 이탈 종료(2026-07-26 추가)**: 새 노드가 생성됐는데 그 활성 경로에 `startedNodeId` 가 없으면 = 방송을 켠 가지를 버리고 다른 길로 간 것 → **즉시 종료**(다시보기로 보존). closing 2연속은 그 가지로 돌아와야만 판정 기회가 생기므로, 이 트리거가 없으면 끝나지 않는 방송이 쌓인다. 되감아 보기만 한 상태(생성 없음)는 종료하지 않고 화면만 "대기", 수동 새로고침(force)도 종료 판정을 하지 않는다.
- **시청자 수 모델**: 시작값 = 스트리머 followers × 1~3% + 이슈 보정. 이후 매 노드 모델이 제시하되 엔진이 직전값 대비 ±60% 로 클램프(순간이동 방지). 도네이션은 채팅 항목의 선택 필드(금액+메시지), 큰 이슈·큰 사건에서만 고액.
- 채팅 생성도 §6.3 알고리즘 분배(호의 8할, 이슈 커지면 불호 40%까지) + 계정 DB 재등장 우선. "장면 속 인물은 시청자로 등장 금지" v1 규칙 유지.

### 7.4 콘텐츠 스탠스

- 기본 프롬프트는 **허용 기조로 작성**: 방송 내용이 nsfw·서사 내 범죄·협박·비자발 송출이어도 우리 시스템이 걸러내지 않는다 — 시청자 반응은 그 상황에 맞는 리얼한 반응(신고 언급, 동조, 공포 등 서사적 반응 포함)으로 생성하라고 지시. 검열 여부는 사용자가 쓰는 AI 모델의 권한.
- 이 기조는 편집 가능한 미디어 프롬프트(`phoneTube` 버킷 신설)에 두어 사용자가 수위를 직접 조정.

### 7.5 UI

- 홈: 스텔라튜브 아이콘(LIVE 시 빨간 점 배지). 앱 화면 = 방송 중이면 라이브 뷰(§2.2), 아니면 다시보기 목록.
- 라이브 뷰: 방송 화면(세션 최근 장면 텍스트, 활성 삽화 있으면 썸네일) + 실시간 채팅(노드별 채팅을 시간순 스크롤, 새 노드 반응 도착 시 하단 append — 통짜 재렌더 금지) + 시청자 수/도네이션 오버레이.
- **채팅 번역(구현 완료)**: 방송 화면은 삽화+채팅뿐이라(장면 프로즈 없음) 번역 대상 = 시청자 채팅 텍스트만. `StreamChatItem.translation` + `translateStream`(문자/SNS 와 같은 엔진), 자동 번역 켜지면 노드 반응 생성 시 인라인 번역, 햄버거 [원문/번역 보기]+[방송 채팅 다시 번역]. 번역 표시/토글/재번역은 문자·SNS·방송 공통 배관(`PhoneTranslateKind`)으로 통일 — 새 앱도 이 축에 얹으면 번역 UI 가 따라온다.

## 8. 앱 간 정보 공유 허브

### 8.1 공유 다이제스트

```
buildSharedDigest(excludeApp, budget = sharedContextTokens 기본 1000):
  소스별 기여 (각 앱이 공급자로 등록 — §9 확장도 같은 목록에 참여):
    messages : 최근 스레드별 마지막 대화 한 줄 요약 (상위 5)
    sns      : 등급 내림차순 최근 이슈 요약 줄 (게시자/등급/한 줄, 상위 10)
    tube     : 진행 중/최근 방송 (스트리머, 무엇을 방송, 반응 규모)
  excludeApp 제외 → 합쳐 trimToTokens(budget)
```

- 설정: `sharedContextEnabled` 기본 **켬**, `sharedContextTokens` 기본 **1000**(각 앱 자기값 제외).
- 문자 답장·SNS 배치·튜브 반응·엑스트라 문자 생성 입력에 전부 합류. 캐시(`shared-digest.json`)는 각 앱 저장 이벤트에 무효화되는 파생 데이터.

### 8.2 "봤는지" 판정 (1:1 문자용)

문자 상대가 공유 이슈를 아는지의 판정:

```
saw(char, item):
  그 캐릭터가 그 글/방송에 답글·코멘트·채팅을 남겼음 → 100% (판정 없이 안다)
  아니면 결정적 해시 hashRatio(itemId + charKey) < p(issueScale)
    p = {1: 5%, 2: 20%, 3: 50%, 4: 70%, 5: 90%}
```

- **결정적 해시**를 쓰는 이유: 같은 캐릭터는 같은 글을 "봤거나 못 봤거나" 가 재생성해도 일관 + 세션 주입 경로(phone 슬롯)의 미리보기 byte 동일 대전제 유지. 다이제스트에서 못 본 항목은 그 상대의 프롬프트에서 제거(아예 안 준다 — "모르는 척 지시"보다 확실).
- SNS 세션 주입의 v1 확률 규칙(작성/답글 100%, 나머지 30%)은 이 p 테이블로 대체(등급 기반으로 승격).

| 축 | 비중(기본) | 재료 | 규칙 |
|---|---|---|---|
| **일상 축** (기본이자 다수) | 7 | 인물 프로필 + 로어북 + 계정 성향 메모 + 시간대 | 화면 밖에서 지금 뭘 하고 사는가. 세션과 무관하므로 스토리를 앞지르지 않는다 |
| **사건 축** | 3 | 진행분이 있는 세션의 새 구간 | 그 자리에 있던 **당사자 본인**만, 공개할 만한 슬라이스만 |

- 비율은 설정(`snsDailyRatio` 등)으로 조절. **진행분이 없으면 10:0** = 잡담 모드(사건 축 0, 새 플롯 사건 발명 금지).
- **금지/허용 경계**(프롬프트에 명시): 본편 줄거리를 진전·해결·확대하는 사건은 금지. 그 인물의 사생활·일상·다른 세계 사람과의 교류는 자유(오히려 리얼함의 핵심 — 유저와 함께 있지 않은 시간의 삶).
- NPC 가 남의 사건을 연구 보고하듯 논평하는 패턴 금지 — 사건 축 재료가 애초에 당사자에게만 주어진다.

**진행분 추적(북마크)**
- 세션마다 "어디까지 SNS 에 반영했는지" 마크를 저장. 갱신 시 **북마크 이후 새 진행분이 있는 세션만** 사건 축 재료로 첨부하고, 첨부 후 북마크를 옮긴다(같은 장면이 다음 갱신에 또 "새 사건"으로 소비되지 않음).
- 정지된 세션은 사건으로 첨부하지 않는다. 대신 그 참가 인물의 "근황 메모" 한두 줄(마지막 요약 축약)만 과거형으로 — 일상 축 재료. 토큰도 크게 절약된다.
- **지식 격리**: 사건 블록마다 "이 일은 X·Y 가 겪은 일이고 다른 인물은 모른다. 그들이 아는 건 피드에 올라온 글과 방송뿐"을 명시. 세션 본문 = 당사자의 사적 경험 / 피드 = 공개 정보로 프롬프트 구조를 나눈다.

## V3-3. 리스트(팔로우) — 등장 범위와 사건 범위의 분리 (구현 완료)

> 구현됨(빌드·하네스 통과, 수동 검증 대기). 배선은 `구현현황.md` V3-3.
> **아래 "저장은 피드 1개 유지" 항목은 V3-7 에서 뒤집혔다** — 리스트는 이제 독립 서버이고 글·계정에 소속 도장이 있다. 이 절은 등장/사건 범위 분리의 원칙만 유효하다.

- **UI 용어 = "리스트"**(트위터 리스트). 그룹 세션의 "그룹"과 겹치지 않게 확정.
- **리스트 = 세션(세계관) 묶음.** 팔로우 버튼은 몰입용 표현이고, 실제로 하는 일은 "이 세션의 사건을 내 피드에 반영".
- **사건 범위 = 리스트에 담은 세션에서만. 등장 범위 = 모든 봇에게 열림**(답글·잡담). 단 **리스트별 밴 목록**에 올린 인물은 그 리스트 피드에 일절 등장 금지.
- 기본 화면: 리스트가 비면 **"아직 팔로우한 계정이 없습니다"** + [팔로우 관리]만. 생성도 돌지 않는다(비용 0).
- 추가 방법 3종: 캐릭터 단위 체크 / **세션 단위**(고르면 그 세션 참가자 전원, 그룹이면 멤버 전원) / "최근 세션 봇 모두 추가" 원클릭.
- 저장은 피드 1개 유지, **생성 범위만** 리스트로 제한(리스트별 피드 파일 분리 안 함 — 마이그레이션·전환 비용 회피). 리스트 칩이 보기 필터를 겸할 수 있다.
- 기존 "SNS 참가 시나리오(제외 목록, `snsExcludedScenarioIds`)"는 리스트로 대체 — 같은 뜻의 설정을 둘 두지 않는다.

## V3-4. 계정 등급 3단계 — 엑스트라가 판치지 않게 (구현 완료)

> 구현됨(빌드·하네스 통과, 수동 검증 대기). 배선은 `구현현황.md` V3-4.
> 승격(엑스트라 → 고정 캐릭터)과 계정 화면 밴/밴 해제도 여기서 함께 붙였다(V3-5 잔여 해소).

**문제 원인(코드 확인)**: 작성자 귀속(`charByName`)이 **시나리오 이름만** 캐릭터로 인정한다. 로어북 인물은 등급이 아예 없어 전부 신규 엑스트라로 떨어지고, 신규 계정 상한을 넘겨도 "등록 없는 익명 작성자"로 글이 그대로 나가서 엑스트라가 사실상 무제한이었다.

| 등급 | 정의 | 등장 빈도 |
|---|---|---|
| 1. **캐릭터 시나리오** | 시나리오 자체가 인물(카드 이름 = 사람 이름) | 최다 |
| 2. **로어북 캐릭터** | 세계관/타이틀 시나리오의 로어북에 등록된 인물 | 중간 |
| 3. **엑스트라** | 즉석 NPC, 본편에 없고 SNS 에서만 태어난 계정 | 최소 |

**설계**
- **캐스트 명부 사전 구축**: 배치 전에 "계정으로 쓸 수 있는 인물 명부"를 만들어 프롬프트에 `@handle — 이름 (세계) — 한 줄 성향` 리스트로 **명시**한다. 지금은 로스터가 설명+로어북 덤프라 모델이 이름을 스스로 찾아야 하고, 실패하면 새 이름을 발명한다 — 명부 명시가 재등장률에 가장 큰 효과.
- **등급 2 확보**: 로어북 엔트리에서 인물을 **AI 자동 선별**(기존 로어북 선별 배관 재사용) + 계정 관리 화면에서 수동 체크 보정. 한 번 등록하면 계정 DB 에 등급 2 계정으로 영속.
- **배분 강제**: 프롬프트 지시 + **파서 검증** — 배치 활동 중 등급 1·2 비율 하한(기본 70%)을 두고 미달분의 엑스트라 활동을 잘라낸다. 지시만으로는 안 지켜진다.
- **엑스트라 상한 실효화**: 신규 계정 상한 초과 시 "등록 없는 익명 작성자"로 통과시키던 폴백을 없앤다(초과분은 폐기하거나 기존 계정으로 대체).

## V3-7. 리스트 = 독립 서버 (2026-07-31 사용자 확정, 구현 완료)

> 구현됨(빌드·하네스 통과, 수동 검증 대기). 배선은 `구현현황.md` V3-7.
> V3-3 은 "생성 범위만 제한, 피드는 볼트 공용"이었다. 그래서 **세션이 받는 SNS 정보가 리스트와 무관**했고, 리스트를 나눠도 세계들이 서로의 소식을 알았다. 리스트를 만든 목적(세션별 공유 정보 제한)이 달성되지 않던 지점.

**확정 규칙**

- **활성 리스트 = 지금 접속 중인 서버.** 한 번에 하나만 켜지고, 표시·생성·세션 주입이 전부 이 하나를 본다.
- **세계는 여러 리스트에 담길 수 있다**(중복 소속 허용). 어느 순간에 유효한 건 켜진 서버뿐이라 모호함이 없다.
- **글·계정에 소속 도장.** 피드/계정 관리/알림/붐업 이슈/보관 한도(200)가 전부 서버별.
- **세션 주입 게이트**: 세션 참가자(호스트 + 그룹 멤버)가 활성 서버에 담겨 있을 때만 SNS 발췌가 들어간다. 아니면 **SNS 는 그 세션에 존재하지 않는다**. **문자·방송은 서버와 무관하게 계속 동작**한다.
- **자동 트리거도 활성 서버에만.** 비소속 세션의 키워드/랜덤 트리거는 문자·방송만 돌리고 네트워크에는 참여하지 않는다. 비소속 세션의 방송은 피드 카드도, 서버 주민 시청자도 없다(무소속 시청자).
- **공유 허브도 서버 경계를 지킨다.** SNS 로 가는 다이제스트에는 활성 서버 밖 방송·글이 실리지 않고, 문자로 가는 다이제스트는 상대가 활성 서버에 있을 때만 SNS 조각을 받는다.
- **리스트 삭제 = 서버 폐쇄.** 그 서버의 글·계정도 함께 사라진다(남기면 어디서도 못 보는 유령 데이터).
- **이관**: 도장 없는 옛 글·계정은 최초 로드 1회에 활성 리스트로 옮긴다. 리스트가 없던 볼트는 글에 등장한 세계들로 "내 피드"를 만들어 담는다.

**알아둘 부작용** — 서버를 전환하면 같은 세션이 받는 SNS 기억도 바뀐다(설계상 당연한 결과). 자주 갈아끼우면 캐릭터 기억이 널뛰는 것처럼 보인다.

# 번역 회귀 방지 규칙

> 이 영역을 수정할 때만 읽는다. 규칙은 실제 사고에서 얻은 불변식이며, 구현이 바뀌면 현재의 올바른 경로만 남도록 갱신한다.

- **번역 보기의 편집 기능을 양방향 번역(집필 프로) 전용으로 두지 않는다.** — "문단 통째 선택 → 삭제 → 원문에서도 삭제"(`performTranslationStructuralDelete`)가 `bidirectionalWriting()` 게이트 뒤에 있었다. 양방향이 꺼져 있으면 삭제 키가 브라우저 기본 동작으로 처리돼 DOM 에서만 사라지고, `commitTranslationEditSync` 는 **떨어져 나간 블록(`!contains`)과 빈 값(정규화 아티팩트 방어)** 을 둘 다 무시하므로 **아무 데도 저장되지 않는다** → 다음 재렌더에 지운 문단이 되살아난다(2026-07-31 수정, 편집 조용한 유실). 번역 보기는 "직접 편집이 기본 모드"이므로 **편집 동작 자체는 토글과 무관**해야 한다 — 양방향 전용인 것은 대기함(`pendingReflections`) 기록과 끝의 초고 영역뿐이다. 번역 보기에 새 편집 동작을 붙일 때 게이트를 어디에 거는지 확인한다.

- **contenteditable 의 삭제를 keydown 만으로 잡지 않는다.** — 모바일 소프트키보드는 Delete/Backspace keydown 을 안 보내거나 키를 식별할 수 없고, 잘라내기·컨텍스트 메뉴 삭제도 keydown 이 없다. 같은 판정을 `beforeinput`(`inputType.startsWith("delete")`)으로도 받는다. keydown 이 이미 `preventDefault` 했으면 beforeinput 은 오지 않으므로 중복 처리는 없다.

- **문단 키에서 "앞 문단"을 빼지 않는다 — 내용만으로 키를 잡으면 반복 대사의 번역이 통째로 공유된다.** — 키가 내용 해시뿐이던 시절, 챗에서 반복되는 짧은 대사(`"No."` `"응."`)가 전부 한 항목으로 합쳐졌다. 맨 처음 번역된 하나가 그 뒤 모든 위치에 그대로 재사용돼 **"남은 거 있어?"의 답 "없습니다"가 "안 와?"의 답 자리에도 나왔고**, 그 자리는 AI 를 다시 부르지도 않아 앞 문맥을 붙이든 프롬프트를 고치든 안 고쳐졌다(2026-07-29 사용자 제보 — "번역 질이 떨어졌다"로 접수됐지만 실은 원래 있던 구조 문제, 병렬화로 노출만 늘었다). → 키는 `paragraphKey(내용, 앞 문단)`. 되돌리기 스택·양방향 대기함도 같은 키를 쓴다.

- **문단 키를 쓰는 곳은 "어느 범위를 토큰화했는지"를 반드시 맞춘다 (조용한 실패).** — 키가 앞 문단에 의존하므로 본문 전체를 토큰화한 키와 조각(말풍선/구간/노드)만 토큰화한 키가 **다르다**. 어긋나면 번역이 다 되고 저장까지 됐는데 **화면에만 안 나온다** — 오류도 로그도 없어 원인 추적이 가장 어려운 종류다. 챗은 표시/편집/대기함/내보내기가 전부 말풍선 단위라 특히 위험. → 조각을 토큰화하는 호출자는 `tokenizeParagraphs(조각, lastParagraphSource(앞부분))` 로 앞 문단을 넘긴다. 새 표시 경로를 추가하면 `tests/translate-key-scope.test.ts` 에 등가 검사를 함께 넣는다(전체 기준 키 == 조각 기준 키).

- **앞 문맥 참고 블록에 번역 없는 문단을 담지 않는다.** — 청크를 동시에 띄우면 바로 앞 문단이 아직 번역 중이라 짝이 비는데, 그대로 담으면 **"이미 번역된 직전 문단 — 절대 번역하지 마라"** 는 머리말을 달고 원문만 6줄 나갔다. 지시와 자료가 모순이고 번역 대상 JSON 바로 옆에 같은 언어 원문 덩어리가 붙어, 짧은 문장일수록(챗·폰) 대상이 흐려졌다(2026-07-29). → `collectTranslationContext` 는 active 번역이 있는 문단만 담고, 담을 게 없으면 블록을 안 붙인다. "참고자료가 없는 것"보다 "못 믿을 참고자료"가 나쁘다.

- **폰 번역 항목 id 는 짧은 합성 id(`m0`/`p0`/`c0`…)를 쓴다 — 긴 uuid 를 번역 id 로 넘기지 않는다.** — `translateItems` 는 항목을 id 로 매칭하는데(모델이 응답에 id 를 되돌려줌), 채팅 항목의 긴 uuid 를 그대로 번역 id 로 넘겼더니 모델이 정확히 재현하지 못해 매칭이 전부 실패 → **스텔라튜브 채팅 번역이 통째로 안 됐다**(2026-07-22 사고). → `runChatTranslation` 이 `c${i}` 짧은 id 로 요청하고 결과를 채팅 id 로 되돌린다(문자 `m${i}`·SNS `p${i}` 와 같은 규칙). 새 번역 대상을 추가할 때 반드시 짧은 순번 id 를 쓴다.

- **`translateItems` 는 청크 하나가 실패해도 나머지 청크를 계속 번역한다(부분 성공 최대화).** — 한 청크가 형식 오류/호출 실패면 예전엔 그 자리에서 `ok:false` 로 **뒤 청크를 통째로 버려** "번역 보기 눌러도 뒷부분이 다 원문"이 됐다. → 실패 청크는 건너뛰고 계속, 하나라도 성공하면 `ok:true`(부분 성공 보존), 전부 실패해야 `ok:false`. 취소(`isCancelledError`)만 즉시 중단. 못 채운 항목은 "번역 보기" 재토글(미번역만 다시 시도)이나 개별 재번역으로 메운다. **폰 전용 경로**(세션 `translateParagraphs` 는 이 함수와 무관).

- **생성 시점 1회 시도로 끝나는 자동 처리는 "표시 시점 보충" 경로를 반드시 함께 둔다 (폰 SNS·방송 일부만 번역 사고).** — 폰 자동 번역은 문자/SNS/방송이 **만들어지는 그 순간에만** 돌아서, ①설정을 켜기 전에 쌓인 글 ②청크 실패로 빠진 항목 ③라이브 중 인라인 번역이 놓친 채팅이 영구히 원문으로 남았다. 문서상 복구 수단이던 "번역 보기 재토글"은 **자동 번역이 켜져 있으면 이미 번역 보기 상태라 사용자가 누를 일이 없어** 무용지물이었다(2026-07-26 사고). 방송에 있던 "열 때 자동 채우기"도 `방송당 1회` 절대 가드라 라이브 추가분을 못 채웠다. → `phone-view` 의 `shouldFillTranslations(key, pendingIds)` 게이트: 렌더 시 미번역 항목이 있으면 채우되, **직전 시도와 미번역 집합 지문이 같으면**(= 그 시도로 아무것도 못 채움) 재시도하지 않는다. 절대 1회 가드(진전이 있어도 다시 안 함)도, 무조건 재시도(실패 루프)도 아니다. 수동 토글은 지문을 기록한 뒤 강제 실행해 뒤따르는 렌더가 같은 요청을 또 쏘지 않게 한다. **원문이 바뀌면 옛 번역을 지워** 보충 대상이 되게 한다(라이브 방송 게시글 `syncLiveStreams`).

- **번역 계획(`translationBlocks`)을 본문보다 낡은 채로 쓰지 않는다 — 낡은 계획 하나가 이어쓰기를 영구히 막았다 (2026-08-17 사용자 제보).** — 계획은 그릴 때의 `baselineText` 스냅샷인데, **번역 패널이 숨어 있는 동안(원문 보기)에는 아무도 다시 그리지 않는다.** 원문 보기로 돌아가 이어 쓰고 고치는 동안 계획은 계속 낡고, 그 계획을 소비하는 두 경로가 함께 터졌다: ① 위젯 배치(`placeInlineInTranslation`/`placeNotesInTranslation`/`placeSpeakerLabelsInTranslation`/`renderAiStartMarkerTranslation`)가 `editEl.insertBefore(el, block.el)` 의 기준으로 낡은 span 을 넘겨 **NotFoundError**(`Failed to execute 'insertBefore' … not a child of this node`) — 이 예외가 `renderBodySpans` → `commitPending`/`rebuildBaselineAndRender` 를 타고 올라가 `handleContinue` 의 catch 에 잡혀 **"이어쓰기를 시작하지 못했습니다" 토스트만 반복되고 생성이 아예 안 됐다**(계획을 고칠 렌더도 그 예외로 못 돌아 스스로 풀리지 않는 영구 고장). ② `collectProOps` 가 낡은 `offset`/`source` 로 op 를 만들어 `convertAndSplice` 의 `expect` 검증에 매번 걸렸다("그 사이 본문이 바뀌어 반영을 취소했습니다" — 대기함은 성공해야 비므로 이것도 영구 고장). → 계획 유효성은 `translationPlanMatches()`(문단 해시/원문/offset 일치 **+ 각 블록 el 이 편집면의 직계 자식**) 한 곳에서 판정하고, 계획을 소비하기 전에 `ensureTranslationPlan()`(어긋났으면 숨어 있어도 패널 재구성, 조합/생성 중이면 보류)을 부른다. 삽입 기준 노드는 `translationInsertRef()` 로만 얻는다 — **`contains` 로 검사하면 안 된다**(브라우저가 span 을 다른 span 안으로 옮기면 contains 는 참인데 `insertBefore` 는 던진다). 번역 패널의 계획을 읽는 새 경로를 만들면 이 두 함수를 먼저 태운다.

- **막힌 상태에는 사용자가 스스로 풀 수단이 있어야 한다 (반영 대기 취소).** — 대기함은 **성공했을 때만** 비워진다(재시도 보장). 그래서 끝내 반영될 수 없는 건이 하나 끼면 이어쓰기가 매번 그 반영부터 시도하다 멈추는데, 그걸 비울 방법이 화면 어디에도 없었다 — 사용자에게는 "양방향 번역이 꼬였는데 풀 방법이 없다"가 된다. → 번역 패널(양방향 섹션)의 **'반영 대기 취소'**(`discardPendingReflections`): 대기함·초고를 비우고 대기 문단의 `user-edit` variant 를 `authored` 로 바꾼다(**저자가 쓴 문장은 화면에서 사라지지 않는다** — 되돌리면 유실로 접수된다). AI 를 부르지 않는 순수 변환이라 어떤 실패 상태에서도 성공한다. 열려 있는 세션창은 `handleExternalTranslationsChange` 에서 초고를 다시 받아 온다 — 안 그러면 다음 flush 가 초고를 대기함에 되써서 취소가 되살아난다(미저장 타이핑이 있으면 건드리지 않는다). **재시도 보장을 위해 상태를 남기는 구조를 새로 만들면 그 상태를 버리는 수단도 같이 만든다.**

- **번역 편집 커밋 방어를 무너뜨리지 않는다.** — 브라우저 정규화로 편집 영역에서 떨어져 나간 스팬이나 "내용 있던 문단 → 빈 값" 변경을 커밋하면 번역이 통째로 지워진다. → 그런 변경은 커밋하지 않는다. 빈(공백뿐인) active 번역은 `hasTranslation()` 이 없는 것으로 취급 → 원문 표시 + 재번역 대상으로 남겨 복구 가능.

- **일괄 번역 버튼은 원문/번역/split 어떤 모드에서도 항상 같은 자리에 보인다.** — 모드나 드래그 선택에 따라 버튼이 뜨고 사라지지 않는다. 선택 영역 번역으로 기능이 바뀌면 아이콘(`list-plus`→`list-checks`)과 강조색(`.is-selection`)으로만 표시.

- **번역 뷰는 단일 contenteditable 영역 구조를 유지한다.** — 문단별 contenteditable 섬으로 바꾸면 문단을 넘는 드래그 선택이 막힌다(Chromium 제약). 구분자/재번역 버튼은 `contenteditable=false` 원자 위젯으로 caret 침입 차단.

- **초고(이어쓰기) 영역은 "span 하나 + 진짜 개행"이고, 변환 중에도 편집 가능해야 한다 (양방향 번역 한글 입력 사고).** — 두 결함이 겹쳐 "초고 칸에 입력이 안 되고, 어쩌다 써져도 변환·생성 뒤에 엉뚱한 자리에 끼어 있다"로 접수됐다(2026-07-31 사용자 제보). ① **줄바꿈**: Chromium 은 `.ggai-tr-propending` 안에서 개행이 생기면 그 span 을 **형제 span 으로 쪼갠다**(클래스·id 까지 복제, 개행 문자는 남지 않는다 — 실측). 뷰는 첫 조각만 초고로 읽었으므로 **둘째 줄부터 쓴 글이 어디에도 저장되지 않고** 다음 재렌더(`root.empty()`)에 통째로 사라졌다. ② **변환 중 잠금**: `lockProOps` 가 초고 프리픽스를 `contenteditable=false` span 으로 감쌌는데, 초고 **전체**가 실려 가는 경우(커서가 초고 밖일 때·이어쓰기 flush)엔 초고 영역에 **커서를 놓을 자리가 없어져** 클릭·타이핑이 **바로 앞 문단 속으로** 들어갔다(실측). 그 문단은 수정본으로 커밋되고 다음 변환이 문단을 통째로 다시 써 "사이에 다른 문장이 끼어듦"이 된다. 변환은 수 초~수십 초라 그동안 글을 못 쓰는 것 자체도 집필 도구로선 치명적. → ① 개행은 `beforeinput`(`insertParagraph`/`insertLineBreak`)에서 가로채 `\n` 문자로 직접 넣고(끝 개행은 레이아웃에서 접히므로 `<br>` 필러 — `textContent` 에는 안 잡히고, 이어 쓰기 시작하면 브라우저가 스스로 치운다), 붙여넣기 등으로 쪼개지면 `normalizeProPending` 이 한 span 으로 되돌린다(조합 중이면 미룬다 — 읽는 값은 `readProPendingText` 가 조각을 개행으로 이어 붙여 항상 온전). ② 초고는 **잠그지 않는다** — 변환에 보낸 프리픽스 문자열(`proInFlightTailPrefix`)만 기억했다가 성공 시 `startsWith` 로 덜어낸다(문단 잠금은 유지). **초고 영역의 DOM 구조를 바꿀 때는 "지금 커서를 놓을 자리가 항상 있는가", "브라우저가 이 요소를 쪼개지 않는가"를 먼저 확인한다.**

- **문단/초고 span 의 경계를 넘는 편집(Enter·Backspace·Delete)은 브라우저에 맡기지 않는다 — 브라우저가 우리 영역을 합치고 지운다 (양방향 번역 "입력창이 사라짐" 사고).** — "끝부분을 지우고 내가 쓸 문장을 이어 쓰면 매번 에러 — 입력창이 사라지고 위로 입력 포커스가 가서 붙고, 아래에 입력을 할 수 없다"(2026-08-13 사용자 제보). 실측(Chromium, `contenteditable=plaintext-only`): ① 초고 머리에서 **Backspace** → `.ggai-tr-propending` **span 자체가 제거되고 초고 글이 앞 문단 span 안으로 합쳐진다**(빈 초고에서도 span 이 사라진다 — 빈 초고를 클릭하면 커서가 span 안이 아니라 편집 영역 레벨에 놓이는 경우도 같다). 그 뒤 타이핑은 앞 문단 수정으로 들어가 그 문단이 통째로 다시 쓰인다. ② 마지막 문단 끝에서 **Delete** → 같은 병합. ③ 문단 안 **Enter** → 편집 영역을 `<div>` 로 쪼개며 **문단 꼬리와 초고 span 을 그 div 로 끌고 들어간다** → 문단 스팬은 잘린 채 커밋되고(문단 뒷부분 유실), div 안에 친 글은 초고에도 문단에도 안 잡혀 다음 재렌더에 사라진다. → 경계 편집은 전부 우리가 수행한다: `handleProPendingBoundaryDelete`(초고 머리 Backspace = 앞 문단 마지막 글자만 `deleteData`, 문단 끝 Delete = 초고 첫 글자만 — 서로게이트 쌍 보호, 본문이 개행으로 끝나면 앞이 구분자라 아무것도 안 지운다) + `onTranslationNewline`(Enter 는 항상 `\n` 문자, 문단은 `white-space: pre-wrap` 으로 보이게). `preventDefault` 했으면 `input` 이 안 오므로 `scheduleTranslationCommit`/`onProPendingInput` 을 직접 부른다. **번역 편집면에 새 키 동작을 붙일 때는 "브라우저 기본 동작이 우리 span 을 지우거나 합치지 않는가"를 실제로 눌러 확인한다** — 텍스트 유실은 조용해서 다음 재렌더까지 안 보인다.

- **번역 편집면을 다시 그릴 때 커서와 함께 `focus()` 도 되돌린다 — selection 만으로는 키 입력이 아무 데도 안 들어간다.** — `renderTranslationBlocks` 는 `root.empty()` 로 편집면을 통째로 새로 만드는데 커서를 되돌리지 않았다. 백그라운드 이벤트(외부 번역 저장 → `handleExternalTranslationsChange` → `applyDisplayMode`, 자동 번역 진행 `renderTranslatedSoFar`, 외부 세션 변경)는 **사용자가 쓰는 도중에** 이 경로를 태우므로, 초고를 치던 사람은 "칸은 그대로인데 글이 안 써지는" 상태가 된다 — 발동 시점이 백그라운드 작업이라 재현 조건이 안 보이고, 사용자에게는 "고쳤다더니 또 재발"로 보인다(2026-08-13 제보). 실측: `root.empty()` 후 `document.activeElement` 는 `body` 가 되고, **selection 만 다시 놓으면 커서는 보이는데 타이핑이 들어가지 않는다** — `edit.focus({preventScroll:true})` **먼저**, 그 다음 selection 이어야 한다. → `captureTranslationCaret`(초고 offset / 문단 hash+offset + 그때 포커스 여부) → `restoreTranslationCaret`. **재렌더 직전에 편집면이 포커스를 갖고 있었을 때만** 되돌린다(다른 입력칸 타이핑 중이면 뺏지 않는다). 편집면을 empty() 하는 새 경로를 만들면 이 한 쌍을 반드시 함께 태운다.

- **삭제 후 커서를 문단 머리로 되돌리지 않는다 — 부분 삭제는 잘라낸 자리가 커서 자리다.** — `setCaretAfterProDelete` 가 "삭제 지점 이후 첫 문단"을 찾아 그 **머리**로 커서를 보냈는데, 문단 뒷부분만 지운 경우 그 문단이 곧 "이후 첫 문단"이라 커서가 지운 자리가 아니라 문단 맨 앞으로 튀어 올랐다("위로 포커스가 가서 붙는다"의 다른 원인). → 부분 삭제로 살아남은 첫 문단은 `{hash, offset}` 을 넘겨 `setCaretWithin` 으로 그 자리에 놓는다(중첩 마커 span 대응 TreeWalker). 통째 삭제일 때만 다음 문단 머리(없으면 초고 영역).

- **타이핑 중인 편집면에서 텍스트 노드를 갈아치우지 않는다 — 다음 첫 글자가 삼켜진다.** — 위 ①의 첫 구현이 개행을 넣을 때 `textContent` 재설정(노드 교체) + `removeAllRanges()` → `addRange()` 로 커서를 다시 꽂았더니, **엔터 다음에 친 첫 글자가 사라졌다**(2026-07-31 사용자 제보). 브라우저의 편집·IME 상태는 그 텍스트 노드와 선택에 물려 있어서, 조합이 시작되려는 순간 노드가 사라지거나 선택이 잠깐 비면 그 입력이 통째로 버려진다(영문 타이핑은 멀쩡해 보여 자동 테스트로는 안 잡힌다). → 커서가 있는 **그 노드에 `insertData` 로 글자만 끼워 넣고**, 커서는 `Selection.collapse(node, offset)` 로 옮긴다(선택이 비는 순간을 만들지 않는다). 노드 합치기(`normalize()`)도 같은 이유로 타이핑 경로에서 쓰지 않는다 — 브라우저는 타이핑 중 텍스트 노드를 여러 개로 남기므로(실측), 위치 계산은 `proPendingCaretTarget` 처럼 **노드를 건드리지 않고 offset 만 환산**해서 한다.

- **contenteditable 편집 영역은 `user-select: text` 를 명시한다 (번역 보기 클릭-커서 안 생김 사고).** — 옵시디언 앱은 UI 크롬 기본값으로 `user-select: none` 을 상속시킨다. `.ggai-tr-edit`(번역 편집면)가 이걸 안 되살려, 클릭으로 caret 을 놓는 것이 막혔다(JS 로 `setCaretOffset` 하면 들어가지만 마우스 클릭은 안 됨 — user-select:none 의 정확한 동작). 렌더/생성/분기이동 직후엔 코드가 caret 을 꽂아줘 편집이 되다가, **분기 패널에서 하위라인 삭제**처럼 편집면이 비활성인 채 패널이 재구성되면 caret 이 안 꽂혀 커서가 사라지고, 클릭으로도 못 만들며, 세션 탭을 껐다 켜도(열 때 번역면에 caret 을 안 꽂음) 안 풀렸다. → 새 contenteditable 편집 표면은 `user-select: text`(+`-webkit-`)를 반드시 켠다. 원문 본문(`.ggai-session-body`)은 편집 호스트 자체라 UA 가 caret 을 허용해 안 걸렸을 뿐, 중첩 span 으로 편집면을 구성하는 표면(번역/파생)은 명시가 필요하다.

- **번역 결과는 "요청한 대상 문단"만 기록한다 — 참고로 보여준 앞 문맥은 기록 금지.** — 앞 문맥/앞 번역은 `{{main}}` 밖(로어북 위치)에 `collectTranslationContext`/`formatTranslationContext` 로 "번역 금지" 참고 블록으로만 붙는다({{main}} 에는 대상 문단만 — 예전처럼 `context` 세그먼트를 {{main}} 에 끼워 보내지 않는다). 그래도 응답에 대상 아닌 문단이 섞여 오면 무조건 `recordTranslationVariant` 하지 말 것 — 요청하지 않은 옆 문단(특히 집필 프로 저자 원고 `authored`)을 기계 번역으로 덮어쓴다(2026-07-21 사고). → `translateParagraphs`/`previewTranslateRange` 는 `chunk` 의 대상 해시 집합에 든 응답만 기록/미리보기에 담는 방어를 유지한다.

- **사용자가 시키지 않은 순간에 AI 를 부르지 않는다 — 특히 글 쓰는 도중에는.** — 양방향 번역(소설)의 집필 변환이 "타이핑이 3초 멈추면 자동"이었다. 저자에게는 **발동 조건이 안 보인다**: 문장을 고민하다 멈춰도, 보기(원문↔번역)를 전환했다 돌아와도(재렌더가 반영을 재예약했다) 변환이 터졌고, 끝나면 화면이 다시 그려지며 **초고 입력란이 비워져** "에러가 났나? 내가 잘못 쓰고 있나?"가 됐다(2026-08-01 사용자 제보). 덤으로 쓰다 만 문장이 그대로 AI 에 나가고(오요청), 타이핑 중 재렌더가 커서·한글 조합을 끊었다. → 대기분은 **대기함에만 쌓고**, 반영은 **사용자가 생성을 요청할 때**(이어쓰기/미리보기) `runProConvert()` 한 번으로 처리한다. **자동 실행을 새로 넣을 때는 "사용자가 그 순간 무엇을 눌렀는가"로 정당화되는지 본다** — 재렌더·보기 전환·타이머는 사용자의 의사 표시가 아니다. 화면 안내 문구(placeholder·? 도움말)도 발동 조건의 일부이므로 함께 맞춘다.

- **양방향 반영은 "생성 락"이 아니라 "생성 요청 시 일괄 처리"다 (2026-07-28 사용자 교정).** — 전송/이어쓰기 버튼은 항상 눌리는 상태여야 하고, 누르면 그 자리에서 필요한 반영(말풍선 수정·초고 변환)을 전부 처리한 뒤 출발한다. **과거 실패를 이유로 요청을 거부하지 않는다** — 누를 때마다 새로 시도하고, 방금 그 시도가 실패했을 때만 멈춘다. 알림은 반영 실행부가 띄운 1회로 충분(게이트에서 중복 토스트 금지). 버튼 비활성화·조용한 no-op 로 생성을 막아 두면 사용자에겐 "왜 생성이 안 되지"로 보인다.

- **집필 프로 "반영 대기"는 반영이 끝나면 옛 문단에서도 풀어 준다.** — 대기 판별은 `active 번역 variant.kind === "user-edit"` 하나뿐인데, 한국어 수정을 영어판에 반영하면 **새 영어 해시**만 authored 로 바뀌고 수정 전(옛 영어) 문단의 user-edit variant 는 그대로 남았다. 그 뒤 전 노드로 되돌리기(undo)를 하면 옛 문단이 활성 경로로 돌아와 다시 대기로 잡히고, `renderTranslationBlocks` 의 자기회복 `scheduleProConvert` 가 영어판을 재변환(재생성)했다(2026-07-21 사고 — "되돌리기만 했는데 수정으로 오인해 영어판 재생성"). → `convertAndSplice` 성공 시 교체된 옛 영어 문단들의 해시로 `resolvePendingEditVariants` 를 호출해 active 를 직전 비-user-edit variant(없으면 미번역)로 되돌린다. variant 는 지우지 않는다(다이어트 몫). append(초고 끝쓰기)는 옛 문단이 없어 대상 아님.

- **화면 요소를 만들어 내는 설정 토글은 `applySettingsOnlyChange` 에 반영 경로를 함께 넣는다.** — 설정 패널의 저장은 `kinds:["settings"]` 로 오고, 세션창은 그 경로에서 본문을 다시 그리지 않는다(픽셀 보존이 목적). '양방향 번역'을 켜도 번역 보기 끝의 초고 입력란이 **그 자리에서는 안 생기고**, 보기 토글·생성·문단 편집 같은 다른 이유로 `renderTranslationBlocks` 가 돌 때만 뒤늦게 나타났다 — 사용자에겐 "켰는데 안 뜬다 / 가끔은 뜬다"로 보인다(2026-07-30 수정). → `applySettingsOnlyChange` 가 직전 양방향 상태(`proRenderedBidirectional`)와 비교해 바뀐 순간에만 번역 블록을 다시 그리고, 켤 때는 대기함 초고를 복원·끌 때는 화면에서 지우기 전에 대기함에 남긴다. **설정 하나가 UI 유무를 좌우하면 그 토글의 반영 경로를 직접 확인한다**(출력 방식 전환만 처리하던 자리다).
